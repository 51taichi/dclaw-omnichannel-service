# 老客户历史加载与会话标识设计

## 背景

客户将已有企微账号接入 Bot 时，企微中通常已经存在大量老客户。当前系统只要第一次收到某个客户的普通私聊消息，就会新建流程会话并从任务入口节点开始交流，导致老客户被当成新客户重新询问和引导。

本设计只处理“首次收到老客户消息时即时加载历史”的场景。推送页“同步名单”的批量同步能力不在本次范围内。

## 已验证的 WorkTool 接口边界

已使用正式环境 Bot `wtepxwfy1djl35t5q8999kp6qssnzlmo` 实测：

| 接口 | 实际用途 | 阿三 | 魔兮 |
| --- | --- | ---: | ---: |
| `/robot/wework/message` | 查询 WorkTool 保存的客户侧历史消息 | 62 条 | 244 条 |
| `/wework/listRawMessage` | 查询通过 WorkTool API 下发的指令 | 112 条 | 746 条 |

验证结论：

- `/robot/wework/message` 可以按联系人名称和时间查询客户历史发言，返回文本、图片、语音、合并记录等消息类型。
- `/robot/wework/message` 返回的样本全部为 `sender = 0`，不能获得员工在手机企微中手工发送的历史回复。
- `/wework/listRawMessage` 只包含通过 WorkTool API 主动下发的内容，不能替代客户历史消息接口。
- 两个接口的数据可以按时间合并，形成“客户发言 + 系统 API 发送”的历史上下文。
- “魔兮”修改备注为“魔兮-18570860666”后，按原名称查询仍返回了改名前后的记录；接口具备一定的备注变更关联能力，但缺少稳定联系人 ID，同名客户仍有误匹配风险。
- `/robot/wework/message` 已被 WorkTool 标记为“将废弃”，因此必须封装在独立适配层中，不允许业务流程直接依赖其原始响应结构。

## 目标

- 将“本地没有既有会话且本次消息不是新增好友系统问候”的私聊联系人识别为老客户。
- 在首次回复前加载可获得的客户历史消息。
- 根据导入的客户历史和 Agent 当前标签规则自动打标签。
- 老客户首次本地建档时不把接入日期误写成“添加日期”标签。
- 老客户直接进入任务流程最后一个节点，不从入口节点重新交流。
- 将系统 API 发送历史作为补充上下文异步缓存，不阻塞客户首次回复。
- 在会话卡片姓名右侧显示金黄色“老客户”徽标，并展示历史同步结果。
- 接口失败、超时或没有历史时仍能继续接待客户。

## 非目标

- 不实现推送页“同步名单”的批量老客户导入。
- 不从 WorkTool 同步客户标签。
- 不尝试获取员工在手机企微中手工发送的历史回复。
- 不保证识别同名联系人。
- 不修改新好友系统问候触发的现有新客户流程。
- 不要求 `/wework/listRawMessage` 的首次全量缓存完成后才回复客户。
- 不为本次功能新增可配置的老客户接入节点。

## 老客户识别

识别只应用于私聊消息。处理当前消息前先读取本地状态，避免当前消息落库后被误判为已有会话。

满足以下全部条件时认定为老客户：

1. 消息属于外部联系人或内部联系人私聊。
2. 本地不存在该 `conversationKey` 对应的既有会话周期和流程会话。
3. 消息不是 canonical 新增好友系统问候“我已经添加了你，现在我们可以开始聊天了”。
4. 当前 Bot 已启用并绑定 Agent。

识别结果不依赖历史接口是否返回数据。历史为空、接口失败或接口超时都只影响历史同步状态，不改变老客户判定。

新增好友系统问候始终优先于老客户识别。已标记为老客户的联系人以后若出现有效新增好友系统问候，现有好友重新添加逻辑会开启新的会话周期，并清除老客户来源标识，使其重新从入口节点开始。

## 数据模型

### 流程会话来源

在 `flow_sessions` 增加：

- `customer_origin`：`new`、`legacy` 或 `unknown`，旧数据默认 `unknown`。
- `history_sync_status`：`not_required`、`loading`、`success`、`empty` 或 `failed`。
- `history_imported_count`：成功导入的客户历史消息数量，默认 `0`。
- `history_synced_at`：最近一次历史同步完成时间。
- `history_sync_error`：最近一次失败的简短错误信息，不向普通员工显示原始响应。

老客户流程会话创建时以一个数据库事务写入：

- 最后任务节点；
- `customer_origin = legacy`；
- `history_sync_status = loading`。

### 导入消息去重

在 `conversation_messages` 增加：

- `source`：`local`、`worktool_customer_history` 或 `worktool_api_history`，旧数据默认 `local`。
- `source_key`：外部历史记录的稳定去重键。

为非空 `source_key` 建立 `(bot_id, source, source_key)` 唯一索引。

客户历史接口没有消息 ID，因此 `source_key` 使用以下字段的规范化内容计算：

- Bot ID；
- 响应中的联系人标题；
- `sender`；
- 消息类型；
- 创建时间；
- `itemMsgList` 原始内容。

重复触发、接口重复返回和服务重启不得产生重复历史消息。

### API 指令缓存

新增 Bot 级 `worktool_api_message_cache` 表，至少保存：

- Bot ID；
- WorkTool `messageId`；
- 指令在 `body.list` 中的序号；
- 目标名称；
- 指令类型；
- 可供 Agent 阅读的文本内容；
- WorkTool 创建时间；
- 原始指令 JSON；
- 缓存写入时间。

唯一键为 `(bot_id, message_id, command_index, target_name)`。

该缓存用于把 `/wework/listRawMessage` 的全 Bot 数据按客户索引，避免每个老客户首次发言时都重新全量读取。

## WorkTool 适配层

新增独立历史适配模块，对业务层只暴露规范化结果：

- `listCustomerHistory({ robotId, title, startTime, endTime })`
- `refreshApiMessageCache({ robotId, stopAtKnownMessageId })`
- `listCachedApiMessages({ robotId, targetNames })`

适配层负责：

- 分页；
- 超时；
- WorkTool 响应码校验；
- `itemMsgList` 和 `body` JSON 解析；
- 消息类型归一化；
- 空内容过滤；
- 去重键计算；
- 结构化日志；
- 将 WorkTool 接口变化隔离在单一模块中。

`/robot/wework/message` 按当前联系人标题查询全部可获得历史。只接受响应中与当前 Bot 一致的私聊记录，并将“当前回调标题 + WorkTool 返回标题集合”作为本次会话的联系人别名集合。API 指令缓存使用整个别名集合匹配目标名称，使“魔兮”改为“魔兮-18570860666”后仍可补齐改名前后的 API 发送记录。标题集合同时写入日志，便于排查备注变化和同名误匹配。

## API 指令缓存策略

`/wework/listRawMessage` 不能按客户名称筛选，实测一次读取当前 Bot 的 1360 条记录约耗时 30 秒，因此不得进入客户消息的同步等待链路。

缓存策略：

1. 服务启动后为启用的 Bot 异步刷新一次。
2. 后台按固定周期增量刷新。
3. 每次按创建时间倒序读取，遇到已经缓存的 `messageId` 后停止继续翻页。
4. 初次无缓存时允许完整回填，但只在后台执行。
5. 同一个 Bot 同一时刻只允许一个刷新任务。
6. 刷新失败记录告警并等待下一周期，不影响消息接入和 Agent 回复。

老客户首次处理中只读取当时已经存在的缓存；缓存尚未完成时，先使用客户历史和本地 `outgoing_messages`。后续刷新完成后，将匹配该客户的 API 发送记录幂等补入 `conversation_messages`。

## 首次消息处理流程

1. 接收并去重 WorkTool 回调。
2. 在持久化当前会话前记录 `hadLocalConversation` 和 `hadFlowSession`。
3. 新好友系统问候继续执行现有新增好友流程。
4. 对符合老客户条件的私聊，以 `conversationKey` 进入单飞锁；并发到达的后续消息等待同一次同步结果。
5. 创建老客户流程会话并定位到最后任务节点。
6. 调用 `/robot/wework/message` 拉取客户历史。
7. 规范化、去重并导入 `conversation_messages`。
8. 使用当前标题和本次查询得到的历史标题作为别名集合，合并本地发送记录和当时可用的 Bot 级 API 指令缓存。
9. 将历史上下文、当前消息、最后节点任务和 Agent 标签规则放入本次 Agent 请求。
10. 按现有 Agent 响应验证网关处理回复、标签变化、节点状态和 WorkTool 发送。
11. 更新历史同步状态并释放单飞锁。

历史导入期间收到的多条客户消息继续使用现有消息合并机制，不能分别触发多个历史查询或多个首次 Agent 调用。

## 历史上下文与标签

历史消息全部保存到本地，但不能无上限传给 Agent。

Agent 上下文按以下优先级构建：

1. 当前合并后的客户消息。
2. 最近的双向对话。
3. 客户历史发言。
4. 更早的系统 API 发送记录。

上下文设置消息条数和字符数双重上限。达到上限时优先保留客户发言和最近对话；被截断的消息仍保留在数据库中。

标签不从 WorkTool 导入。Agent 依据当前 Agent 的标签规则分析导入的客户历史，并通过现有结构化标签决策返回标签变化。标签写入继续经过现有校验、互斥、单向变更和事件记录逻辑。

历史接口为空或失败时，不因缺少证据创建任何普通业务标签。

“添加日期”是新客户系统标签，不由 Agent 判断。老客户真实加好友日期无法从当前两个 WorkTool 接口可靠获得，因此老客户首次本地建档时跳过自动添加日期标签，不能使用本次接入系统的日期冒充真实添加日期。

## 流程节点

“最后任务节点”定义为当前 Agent 流程配置中 `nodes` 数组最后一个有效节点。

- 老客户流程会话创建时直接使用该节点作为 `current_node_id`。
- Agent 请求中的当前任务、目标、规则和节点动作全部来自该节点。
- 历史导入本身不执行最后节点的主动激活消息，避免客户刚发来消息时重复发送流程激活内容。
- 若流程不存在有效节点，则保留现有无流程处理行为，不创建无效流程会话。

## 会话卡片标识

老客户徽标只显示在私聊会话卡片中：

- 位置：客户姓名右侧，位于 `flow-session-name-row` 内。
- 文案：`老客户`。
- 图标：历史记录图标，不使用标签图标。
- 颜色：使用与“人工接手”状态统一的金黄色色系。
- 形态：紧凑徽标，视觉层级低于姓名，高于普通业务标签。
- 移动端保留“老客户”文字，不只显示图标。

徽标颜色复用人工接手的金黄色设计 token，但不复用人工接手的卡片脉冲、高亮边框或排序规则，避免把“老客户来源”误解为“当前由人工接手”。

提示文案根据同步状态生成：

- `loading`：`正在加载历史记录`
- `success`：`已加载历史记录 N 条`
- `empty`：`未查到历史，已按老客户接入`
- `failed`：`历史加载失败，已按老客户接入`

徽标不是业务标签，不进入标签筛选、标签推送、标签规则和标签触发任务。

## 错误处理与降级

- 客户历史接口返回空：标记 `empty`，进入最后节点，不自动打业务标签。
- 客户历史接口超时或失败：标记 `failed`，进入最后节点，正常处理当前消息。
- API 指令缓存失败：保留已有缓存，记录结构化告警，不阻塞客户消息。
- 历史消息部分解析失败：跳过非法记录，导入其余记录，并记录失败数量。
- Agent 分析失败：沿用现有 Agent 重试和失败处理，不回滚已导入历史。
- WorkTool 备注变化：保留响应中的原始标题；会话仍以当前回调生成的 `conversationKey` 为归属。
- 同名客户：记录匹配标题集合和导入数量，作为已知风险，不声称可以完全消除误匹配。

日志至少包含 Bot ID、conversationKey、查询标题、同步状态、WorkTool 返回数、实际导入数、跳过数、耗时和错误分类，不记录 Secret 或 Agent API Key。

## 性能与限流

- 所有 WorkTool 请求继续遵守官方限流。
- 客户历史查询设置独立超时，超时后立即降级，不无限等待 Agent 回复。
- API 指令缓存刷新与客户消息处理使用不同队列。
- 历史导入使用单事务批量写入。
- Bot 级缓存刷新和会话级历史同步都需要单飞保护。
- Agent 上下文必须执行条数和字符数上限，魔兮这类近千条合并记录不能原样全部发送。

## 控制台 API

现有会话列表响应增加：

- `customerOrigin`
- `historySyncStatus`
- `historyImportedCount`
- `historySyncedAt`

不向普通会话列表返回 `historySyncError` 原文。管理员诊断接口或结构化日志可查看错误分类。

## 测试

### WorkTool 适配层

- 客户历史分页、空页和最后一页。
- 文本及非文本消息归一化。
- 非法 `itemMsgList` 局部跳过。
- 客户历史去重键稳定。
- API 指令全量缓存和遇到已知 `messageId` 后停止。
- API 指令按客户名称查询缓存。
- WorkTool 非 200、业务错误码、超时和非法 JSON。

### 数据库

- 老客户来源和同步状态迁移默认值。
- 并发导入和重复导入保持幂等。
- 客户历史与 API 发送历史按时间排序。
- 好友重新添加后清除老客户来源标识。
- 旧会话不被迁移为老客户。

### 服务端

- 无本地会话的普通私聊触发老客户流程。
- canonical 新好友系统问候不触发老客户流程。
- 已有会话不重复同步历史。
- 两条并发首次消息只发起一次历史查询。
- 成功导入后从最后任务节点回复并按规则打标签。
- 空历史和接口失败仍从最后节点回复且不自动打标签。
- 老客户首次本地建档不创建当天的“添加日期”标签。
- API 指令缓存刷新不阻塞首次回复。
- 历史导入不触发最后节点主动激活消息。
- Agent 上下文截断优先保留客户发言和最近对话。

### 控制台

- 只有 `customerOrigin = legacy` 的私聊卡片显示徽标。
- 徽标位于姓名右侧并使用历史图标。
- 徽标使用与人工接手统一的金黄色 token。
- 徽标不触发人工接手的脉冲、高亮和置顶。
- 四种同步状态显示正确提示。
- 移动端保留完整“老客户”文字且不与姓名、日期标签或接手开关重叠。

## 验收标准

- 阿三或魔兮在清除本地会话后发送普通私聊消息，系统将其识别为老客户。
- 系统调用客户历史接口，幂等导入可获得的客户发言。
- 系统直接使用 Agent 流程最后节点处理当前消息。
- Agent 可以基于导入历史和当前标签规则写入有效业务标签。
- 历史接口失败或为空时，客户仍能得到正常回复。
- 会话卡片姓名右侧显示金黄色“老客户”徽标，并能查看同步结果。
- 后台 API 指令缓存不会显著增加客户首次回复等待时间。
- 新好友、已有会话、群聊、人工接手和普通标签流程保持现有行为。
