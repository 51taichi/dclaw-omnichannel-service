# 通用动作工具箱设计

## 背景

当前任务状态机和激活话术已经支持“拉人入群”动作，但动作配置被嵌在具体场景里。未来还会出现更多通用工具，例如发送微盘、发送文件、打标签、修改备注、发送资料包等；这些工具不仅会用于任务节点和激活话术，也可能用于人工接管、主动推送、标签触发等场景。

因此动作能力应该从具体场景中抽象出来，成为控制台统一维护和插入的“动作工具箱”。

## 目标

1. 在控制台右侧提供固定悬浮的动作工具箱。
2. 工具箱中展示可用动作工具，第一版仅支持“邀请进群”。
3. 用户在任意支持动作的文本编辑区域中，可以通过工具箱插入动作 chip。
4. 动作 chip 在编辑器中可见，例如 `[动作：拉入 直播课学习群]`。
5. 发给客户的消息中绝不包含动作 chip 文案。
6. 服务端发送纯文本后，再统一执行动作。
7. 后台会话记录保留动作 chip、动作参数和执行结果，方便审计。
8. 动作执行能力复用同一套服务端 action executor，不让每个场景单独实现 WorkTool 调用。

## 非目标

1. 第一版不实现富文本编辑器。
2. 第一版不支持在文本中间按位置穿插执行动作。
3. 第一版不新增除“邀请进群”以外的动作类型。
4. 第一版不修改 Agent 端。
5. 第一版不让客户看到任何动作 chip 原文。

## 交互设计

控制台右侧固定一个“动作工具箱”浮层按钮。点击后打开工具列表。

第一版工具：

- 邀请进群

点击“邀请进群”后弹出参数表单：

- 群名：必填，例如 `直播课学习群`
- 目标：固定为当前私聊客户
- 带聊天记录：默认开启

确认后，系统把动作 chip 插入当前聚焦的文本区域。文本区域可以是：

- 任务节点的完成动作区域
- 激活话术
- 标签触发话术
- 人工接管输入框
- 主动推送文本框

第一版先接入任务节点和激活话术；其他场景复用同一套插入协议逐步接入。

## 发送规则

采用用户确认的 A 方案：

1. 先发送整段纯文本。
2. 纯文本发送时剥离所有动作 chip。
3. 纯文本发送完成后，按动作出现顺序执行动作。
4. 如果文本中只有动作 chip，没有正文，则不发送空消息，只执行动作。

示例：

编辑内容：

```text
我先拉你进直播课学习群，进去后看群公告。[动作：拉入 直播课学习群]
```

客户收到：

```text
我先拉你进直播课学习群，进去后看群公告。
```

服务端随后执行：

```json
{
  "type": "invite_to_group",
  "groupName": "直播课学习群",
  "target": "current_contact",
  "showMessageHistory": true
}
```

## 数据结构

动作 chip 在 UI 中是可读文本，但保存时必须是结构化对象。

通用动作字段：

```json
{
  "id": "action_1",
  "type": "invite_to_group",
  "label": "拉入 直播课学习群",
  "target": "current_contact",
  "params": {
    "groupName": "直播课学习群",
    "showMessageHistory": true
  }
}
```

第一版可以兼容现有字段：

```json
{
  "id": "action_1",
  "type": "invite_to_group",
  "groupName": "直播课学习群",
  "target": "current_contact",
  "showMessageHistory": true,
  "runOnce": true
}
```

后续新增工具时统一扩展 `type` 和 `params`，不改变上层场景的存储方式。

## 执行边界

服务端统一提供 action executor。

动作执行输入：

- botId
- agentId
- conversationKey
- action source，例如 `node_complete`、`activation_sent`、`manual_reply`、`proactive_push`
- action id
- action payload

执行限制：

- `invite_to_group` 第一版只允许私聊会话。
- 群聊会话中如果出现邀请进群动作，服务端跳过并记录日志。
- 当前联系人从 `conversationKey` 解析，不允许前端传任意客户名冒充目标。
- 动作执行失败不影响已发送文本，但必须记录失败原因。
- 重复回调或重复保存不能重复执行同一个动作，继续使用幂等执行表。

## 审计展示

后台会话记录应显示：

- 客户可见文本
- 动作 chip
- 动作执行状态：待执行、成功、失败、已跳过
- WorkTool 返回的 messageId 或错误信息

WorkTool 发送给客户的内容只包含客户可见文本，不包含 chip。

## 测试策略

1. UI 测试：工具箱能生成结构化动作并插入当前编辑区域。
2. UI 测试：编辑器展示 chip，但构建发送内容时剥离 chip。
3. 服务端测试：纯文本先发送，动作随后执行。
4. 服务端测试：只有动作没有正文时不发送空文本。
5. 服务端测试：私聊邀请进群调用 WorkTool type 207。
6. 服务端测试：群聊中的邀请进群动作被跳过并记录。
7. 服务端测试：重复 action id 不重复执行。
8. 回归测试：现有任务节点、激活话术、主动推送、人工接管逻辑不受影响。

## 第一版决策

1. 第一版只接入任务节点和激活话术。人工接管、主动推送、标签触发后续复用同一套工具箱和 action executor 接入。
2. 第一版在普通 textarea 中用文本 chip 展示动作，例如 `[动作：拉入 直播课学习群]`。后续如需要更强交互，再升级成不可误删的视觉 chip。
3. 第一版会话记录展示动作执行状态和失败原因，但不提供手动重试按钮。

这样第一版可以先把通用动作协议和右侧工具箱跑通，同时避免一次性改动人工接管、主动推送和标签触发的发送链路。
