# 群账本跨周期累计聚合补强设计

## 背景与缺口

完成审计发现：群定时任务的最终判断会把原子事实限制在当前日、周或月周期内，这能防止旧事实误判当前任务，但也会使 `{{累计上课次数（从本群建立至今……）}}` 之类明确累计变量看不到历史周期。直接把建群以来全部事实再次提交给 Agent 会让上下文随群寿命线性增长，违背既定的账本压缩原则。

## 方案比较

### 方案 A：累计变量直接读取全部历史事实

实现最少，但群时间越长，请求越大；最终仍会触发请求裁剪并产生累计漏算，不采用。

### 方案 B：每个模板变量维护独立 Agent 累加器

可支持任意白话规则，但同一事实会被多个任务重复计算；模板修改、历史纠正和任务复制都需要复杂的失效与重算状态，不符合“每群一套共享账本”的产品原则，不采用。

### 方案 C：从共享原子事实维护持久化分类聚合

采用此方案。每个群按事实类别维护一条持久化聚合，保存有效事实数、结构化数值字段合计、起止时间和代表性事实/消息证据。累计变量只读取这些有界聚合；当前周期变量继续读取当前周期原子事实。完整原子事实及全部消息证据仍保留在数据库，聚合只是可重建投影。

## 数据模型

新增 `managed_group_fact_aggregates`：

- `bot_id + group_id + category` 唯一标识；
- `fact_count`：该类别当前有效原子事实数；
- `numeric_sums_json`：事实 `value` 中所有有限数值字段按稳定字段路径求和；
- `first_happened_at` / `last_happened_at`：有效事实时间范围；
- `evidence_fact_keys_json`：有界的代表性事实语义键；
- `evidence_message_ids_json`：对应的真实入站群消息 ID；
- `updated_at`。

聚合不取代事实表。事实新增、更新、撤销时，在同一事务中重建受影响类别聚合；最后一个有效事实被撤销时删除该类别聚合。Bot 删除和群合并同步处理聚合，群合并后从目标群的完整事实重新构建，避免简单相加造成语义键去重错误。

## 变量范围与请求边界

服务端只把名称或白话规则明确包含“累计”“至今”“从建群”“自建群”等长期范围表达的变量视为累计变量。

- 条件推送：只使用本自然周期有效事实，不读取累计聚合。
- 普通周期汇总变量：只使用本自然周期有效事实。
- 累计汇总变量：读取群级持久化聚合，同时仍可读取本周期事实。

Agent 请求明确说明：聚合只能用于规则要求累计范围的变量。聚合结构有固定类别数和字段长度上限，不携带完整聊天文本。非兜底累计结果仍必须引用聚合中的代表性事实键；服务端把这些键解析回真实入站消息证据后才允许发送。

## 更正、证据与隐私

- 历史事实被更正或撤销后，分类聚合与事实修订链在同一事务中更新。
- 聚合只保存事实键和消息 ID，不复制聊天正文。
- 代表性证据用于执行记录与会话定位；完整事实与完整证据仍可从事实表和修订链审计。
- 聚合、账本、群背景和角色配置均为内部判断材料，不得出现在客户可见汇总中。

## 测试与验收

必须先写失败测试并覆盖：

1. 跨日、跨周事实不进入普通周期变量，但进入累计聚合；
2. 多条课程事实正确累计事实数和数值字段；
3. 撤销历史事实后聚合立即回退且保留修订证据；
4. 累计汇总请求不包含全部历史事实，仍包含有界聚合；
5. Agent 未引用真实聚合事实或尝试用累计聚合回答普通变量时被拒绝；
6. 群合并后聚合按合并后的去重事实重建；
7. Bot 删除清理聚合；
8. 2,000 条群消息和完整项目测试继续通过。

## 完成标准

明确累计变量能得到建群以来的可靠压缩数据；普通日、周、月变量不会被旧周期事实污染；请求上下文不随群消息总量线性增长；所有非兜底输出仍可定位至少一条真实入站群消息。
