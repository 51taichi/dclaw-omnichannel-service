# Bot 数据隔离设计

## 目标

控制台在选中某个 Bot 后，只能读取、修改和展示该 Bot 的业务数据；异步请求也不能把旧 Bot 的结果写入当前界面。

## 边界

- 业务数据以 `bot_id` 为真实租户边界，`conversation_key` 仅是会话标识，不能单独作为授权依据。
- 会话详情、消息、状态事件、改节点、重置会话和回调关联必须同时匹配 `bot_id`。
- 前端切换 Bot 会立即清空前一 Bot 的临时数据；所有异步完成处理必须确认仍处于发起请求时的 Bot 上下文。
- 上传文件使用 Bot 独立目录并要求上传请求提供 `botId`。

## 允许的全局项

服务健康检查、Bot 选择列表、管理员身份、静态 Emoji 数据以及后台 worker 的调度循环可以是服务级全局项。worker 领取任务后必须使用任务行自身的 `botId`，不得读取当前控制台状态。

## 失败处理

若请求的 `conversationKey` 不属于传入的 `botId`，服务返回“flow session not found”，不得泄露该会话是否存在。回调的状态更新按 `botId + messageId` 限定，无法匹配时仅记录本 Bot 的回调日志。

## 验证

新增数据库隔离测试，使用 Bot A/B 的同名结构数据验证：跨 Bot 会话读写、重置和命令回调不能影响对方。新增控制台边界断言，保证 Bot 切换版本号用于保存、任务详情和上传后的回写。
