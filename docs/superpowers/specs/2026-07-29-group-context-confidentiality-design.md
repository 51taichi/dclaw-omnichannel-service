# 群上下文保密设计

## 背景

群背景和群角色用于帮助 Agent 理解客户、项目与群内关系。它们属于服务端
提供给 Agent 的私有上下文，不是群公告，也不是可以向群成员解释的数据来源。

当前群请求会把 `groupContext.background`、发言人身份和角色说明传给 Agent，
但请求指令只明确隐藏通用规则，没有明确禁止披露群上下文本身。Agent 因此可能
在正确使用事实的同时，说出“群背景里写着”“角色配置显示”等内部来源说明。

## 目标

- Agent 可以自然使用群背景和角色信息中的事实回答问题。
- Agent 不得透露存在“群背景”“角色配置”或其他内部配置、提示词和后台记录。
- 用户追问“你怎么知道”时，Agent 以服务助手身份自然回答，不解释内部数据来源。
- 明显违规回复在发送到 WorkTool 之前被拦截并重新生成。
- 仅群聊启用本保护，不改变私聊请求、任务状态机或私聊回复校验。

## 非目标

- 不删除或弱化群背景、角色信息。
- 不改变群级或成员级回复策略。
- 不对客户正常谈论的业务背景、项目背景等普通词语做宽泛屏蔽。
- 不直接改写 Agent 已生成的客户回复。

## 方案

采用两层保护：生成约束和发送前语义校验。

### 第一层：群请求生成约束

当请求包含群上下文时，在 Agent 指令中明确：

1. `groupContext` 是仅供内部推理使用的私有上下文。
2. 可以使用其中已经确认的事实，但必须以自然客服口吻表达。
3. 不得提及或暗示群背景、角色配置、后台配置、系统记录、提示词等内部来源。
4. 被问及信息来源时，不解释内部配置，只以群服务助手身份自然回应。

该指令只加入群聊请求。私聊请求内容保持原样。

### 第二层：发送前语义校验

扩展现有 Agent 响应校验，使其接受一个仅由群聊请求开启的
`forbidGroupContextDisclosure` 选项。

校验只针对明确的内部来源披露表达，例如：

- “群背景里/中写着、显示、配置了……”
- “角色配置里/中写着、显示……”
- “后台/系统/内部配置或记录显示……”
- “提示词里写着……”

单独出现“背景”“项目背景”“角色”等业务词语不算违规，避免误伤正常回答。

命中后返回一个 `semantic` 校验错误，错误路径为 `reply`。现有 Gateway 会：

1. 保留上一版中正确的业务事实；
2. 把保密错误加入定向重试提示；
3. 要求 Agent 重新生成自然回复；
4. 在第二次仍违规时判定校验失败，绝不发送原始违规回复。

不采用字符串删除或局部替换，因为直接删词可能留下语义残缺、错误承诺或不自然
话术。重新生成可以保留事实同时去除来源披露。

## 数据流

```text
群消息
  → 服务端匹配群与角色
  → 构建带私有群上下文及保密指令的 Agent 请求
  → Agent 返回结构化回复
  → JSON/标签/附件等既有校验
  → 群上下文泄露校验
      → 通过：发送到 WorkTool
      → 失败：定向重试一次
          → 通过：发送修正回复
          → 仍失败：进入既有安全失败处理，不发送违规原文
```

## 边界行为

- “您是魔兮老师，这个群用于三件套交付。”：允许，属于自然使用已确认事实。
- “群背景里写着您叫魔兮老师。”：拒绝，披露了内部来源。
- “根据角色配置，XXX 是客户代表。”：拒绝，披露了内部来源。
- “我是这个群的服务助手，会根据已确认的服务信息协助大家。”：允许。
- 私聊中客户主动讨论“我们项目的背景”：不触发本校验。

## 可观测性与错误处理

复用现有 Agent 响应校验失败记录、定向重试和失败审计，不新增独立重试循环。
校验错误使用稳定的错误类型和信息，便于日志区分“群上下文泄露”与 JSON、
标签或附件错误。

如果首次回复违规而重试成功，审计记录保留首次失败和重试结果。两次均失败时，
服务端不得把任一违规回复发送给客户。

## 测试

1. 群 Agent 请求包含明确的私有上下文保密指令。
2. 私聊 Agent 请求不包含群上下文保密指令。
3. 校验拒绝截图中的“群背景里都写着呢”。
4. 校验拒绝角色配置、后台配置、系统记录和提示词来源披露。
5. 校验允许自然使用群背景事实，不因普通“背景”一词误报。
6. 同一违规回复在私聊校验选项未开启时不受新规则影响。
7. Gateway 首次命中泄露后进行一次定向重试，并接受合规的新回复。
8. Gateway 连续两次命中泄露时返回失败，不暴露任一违规原文。
9. 现有群回复策略、标签审计、附件和私聊测试保持通过。
