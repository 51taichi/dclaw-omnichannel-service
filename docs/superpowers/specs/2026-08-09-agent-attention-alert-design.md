# Agent 待处理提醒设计

## 目标

当 DClaw Agent 判断当前客户问题无法可靠回答、需要查询资料或人工确认时，由 Agent 主动返回结构化待处理信号。渠道服务创建一条可审计的待处理提醒，通知人工客服查看，但不自动切换人工接手，也不阻断 Agent 继续处理客户后续问题。

该提醒与客户标签报警共享现有提醒中心、实时推送和消息定位体验，但使用独立的数据类型、图标、颜色和语音提示。语音内容固定为“您有新的待处理提醒”，不得复用“您有新的标签提醒”。

## 非目标

- 不扫描“我先确认一下”“稍后回复”等 Agent 自然语言来猜测是否报警。
- 不把待处理提醒伪装成客户标签，也不改变客户标签规则。
- 不因报警自动将会话切换为人工接手。
- 不暂停 Agent，不阻止 Agent 回答同一客户的其他问题。
- 不把内部报警原因发送给客户。

## Agent 响应协议

普通会话与人工接手同步审计所使用的 Agent 结构化响应增加可选字段：

```json
{
  "attentionAlert": {
    "required": true,
    "reason": "当前知识库无法确认该产品在目标国家的合规状态",
    "evidenceMessageId": "客户消息证据 ID",
    "evidenceText": "客户原话"
  }
}
```

规则如下：

- `required=false` 或缺省表示不报警。
- `required=true` 时，`reason`、`evidenceMessageId` 和 `evidenceText` 必填。
- 证据只能来自本次请求提供的客户消息候选，不能引用 Agent 自己的回复。
- 服务端使用现有证据 ID 与原文校验机制规范化并验证证据，拒绝伪造、错配或不存在的证据。
- `reason` 是面向员工的简短原因，限制长度并作为内部数据保存，不进入客户回复。
- Agent 可以在同一次响应中正常向客户发送合适的过渡回复；报警与客户回复彼此独立。

采用结构化协议而不是关键词扫描，可以覆盖不同客户语言和不同 Agent 表达，同时避免普通客套话误触发。

## 数据模型

新增独立的 `attention_alert_events` 表，不复用 `tag_alert_events`：

- `id`
- `bot_id`
- `agent_id`
- `conversation_key`
- `customer_name`
- `reason`
- `evidence_message_id`
- `evidence_text`
- `occurrence_count`
- `first_triggered_at`
- `last_triggered_at`
- `read_at`
- `created_at`
- `updated_at`

同一 `bot_id + conversation_key` 最多保留一条未读待处理提醒，通过部分唯一索引约束。不同 Bot 和工作区严格隔离。

## 合并规则

- 会话没有未读待处理提醒时，创建新提醒，`occurrence_count=1`。
- 同一会话已有未读提醒时，不创建第二条；增加次数并更新最后触发时间、原因和证据。
- 合并后定位锚点更新为最近一次触发的客户消息，人工点击时看到当前最需要处理的位置。
- 人工将提醒标记已读后，该会话未来再次触发时创建一条新的提醒。
- 仅“新建未读提醒”播放语音；合并更新只刷新界面和次数，不连续播放声音。

合并以会话为单位，而不是依赖 Agent 生成不稳定的问题分类键。提醒详情保留累计次数、首次时间和最后时间，便于人工判断持续程度。

## 服务端处理流程

1. 当前客户消息按现有流程持久化并调用 Agent。
2. 响应网关解析和校验 `attentionAlert`，同时继续完成原有回复、附件、流程和标签校验。
3. 只有最终通过校验并被采纳的 Agent 响应可以创建或合并提醒；失败重试中的草稿不得产生提醒。
4. 客户回复及其他业务数据完成事务性持久化后，服务端写入待处理提醒。
5. 新建提醒发布 `created` 实时事件；合并提醒发布 `updated` 实时事件。
6. 提醒写入或实时推送失败不得导致重复回复客户。数据库写入应具备幂等键，并在客户回复发送前完成确定性落库。
7. 报警不调用人工接手接口，不改变 `handoff_status`。

## 提醒中心与定位

现有提醒中心统一展示两类提醒：

- 标签提醒：保留当前标签图标、样式和“您有新的标签提醒”语音。
- 待处理提醒：使用独立的待处理图标和醒目但不与错误状态混淆的颜色，播放“您有新的待处理提醒”。

待处理提醒卡片展示客户名、Agent 给出的原因、客户证据摘要、累计次数和最后触发时间。点击卡片后：

1. 切换到提醒所属 Bot；
2. 打开对应私聊或群聊会话；
3. 请求包含 `evidenceMessageId` 的消息窗口；
4. 滚动并高亮触发消息；
5. 将该提醒标记为已读。

若原消息已经被清理，仍打开该客户的最新会话，并显示“原触发消息已不在会话记录中”的非阻塞提示。

## 音频策略

新增独立的静态音频资源，例如 `attention-alert.mp3`，内容为“您有新的待处理提醒”。页面预加载标签提醒音频和待处理提醒音频，根据事件类型选择播放。

浏览器未授予自动播放权限时，沿用现有提醒声音解锁机制。音频播放失败不影响提醒入库、未读数量和消息定位。

## 权限与安全

- 列表、流式订阅、标记已读和消息定位继续使用 Bot/工作区访问校验。
- Agent 只能建议报警，不能指定 Bot、会话或任意消息；这些字段由服务端当前处理上下文决定。
- 日志只记录提醒 ID、Bot、会话、触发次数和安全错误分类，不记录完整客户原话或 Agent 隐藏推理。
- `reason` 和 `evidenceText` 在数据库中按业务数据保护，不进入普通运行日志。

## 失败处理

- Agent 未返回报警字段：按无报警处理。
- 字段格式错误或证据不匹配：响应网关按现有结构化响应修复机制重试，不接受未经验证的报警。
- 提醒已存在：原子合并，避免并发产生多条未读提醒。
- SSE 断开：重新连接后从数据库未读快照恢复，不丢提醒。
- 音频失败：保留视觉提醒，不重复创建报警。

## 测试要求

- Agent 响应协议接受合法报警并拒绝缺失原因、伪造证据和 Agent 回复证据。
- `required=false` 不创建提醒。
- 同一会话连续触发只保留一条未读提醒，次数和最新锚点正确更新。
- 标记已读后再次触发会创建新提醒。
- 并发触发不会突破一条未读提醒的唯一约束。
- 报警不会修改人工接手状态，也不会阻止后续 Agent 调用。
- 标签提醒和待处理提醒分别播放正确音频，合并更新不重复播放。
- 点击提醒能跨 Bot 打开会话、加载证据窗口并高亮消息。
- 原证据被清理时安全降级到最新会话。
- 未授权用户不能读取、订阅或修改其他 Bot 的提醒。

## 验收标准

当 Agent 无法可靠回答一个客户问题时，可以在正常回复客户的同时生成一条待处理提醒。工作台首次收到该提醒时播放“您有新的待处理提醒”；同一会话未处理期间再次触发只更新原提醒。人工点击提醒可自动定位并高亮最近一次触发的客户消息。整个过程不自动人工接手、不影响 Agent 继续回答其他问题，并且不改变现有客户标签报警行为。
