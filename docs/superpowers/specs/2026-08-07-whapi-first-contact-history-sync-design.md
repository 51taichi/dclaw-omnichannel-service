# Whapi 首次发现客户历史同步与日期标签设计

## 目标

当服务第一次从 Whapi 收到某个私聊客户的消息、且本地尚无该客户记录时，先获取该 Chat ID 当前可用的历史消息。系统把历史消息安全导入本地，并以可追溯到的最早消息日期生成客户日期标签，避免把一个历史联系人误判成当天新增客户。

日期标签表示“Whapi 当前可追溯到的最早联系日期”，不承诺是 WhatsApp 账号生命周期内绝对的首次联系日期。

## 触发条件

历史同步只在以下条件同时满足时触发：

- 收到私聊 `messages.post` 事件；
- 消息属于已配置且启用的 Whapi Channel；
- 本地不存在该 `conversationKey` 对应的客户会话；
- 该客户没有完成或正在执行的首次历史同步。

群聊、已有本地会话以及非消息事件不触发该流程。`contacts.post` 不作为核心判断依据，因为联系人改名也可能触发该事件。

## 数据流

1. Webhook 通过现有认证、持久化和去重流程进入 Channel worker。
2. 在创建新的私聊客户会话前，系统为 `botId + conversationKey` 申请一次同步权。
3. 调用 Whapi `GET /messages/list/{ChatID}`，按分页参数读取该聊天当前可用的历史。
4. 将历史消息转换为现有 Channel 标准消息结构，并按 provider message ID 幂等写入会话消息表。
5. 当前 webhook 消息继续走现有写入流程；如果它已在历史结果中出现，由 message ID 去重避免重复。
6. 从有效历史与当前消息中选择最早时间，并按照已有北京时间及日期截止时间规则创建日期标签。
7. 完成历史同步后，当前消息继续进入现有人工接手、合并等待、Agent 调用和自动回复流程。

## Whapi 客户端扩展

Whapi 客户端增加一个只负责读取指定聊天历史的方法。输入包括 Chat ID、分页游标或 offset、页大小和排序；输出保持 Whapi 原始分页信息，但不得暴露 Token。

同步器负责分页，不在 server 路由中直接拼装 Whapi 请求。同步器设置最大页数和最大消息数，防止异常账号产生无限拉取。消息按时间升序处理；Whapi 返回缺失或非法时间的消息可以导入，但不能参与最早日期计算。

## 同步状态与并发

本地为每个客户记录以下状态：

- `pending`：尚未尝试；
- `processing`：正在同步；
- `success`：成功读取并完成导入；
- `unavailable`：Whapi 没有返回可用历史，以当前消息作为最早记录；
- `failed`：请求或转换失败，已降级处理当前消息；
- 同步开始、完成时间、尝试次数和安全截断的错误信息。

数据库唯一约束保证同一 `botId + conversationKey` 只有一个状态记录。进程内并发消息共享同一次同步；多进程或重启场景通过持久化租约避免重复执行。过期的 `processing` 状态允许后续重试。

## 降级与错误处理

历史查询不是客户消息处理的硬依赖：

- Whapi 超时、限流、返回异常或无历史时，当前 webhook 消息仍必须保存和处理；
- 此时用当前消息时间生成日期标签；
- 状态记录为 `failed` 或 `unavailable`，允许以后由后台重试；
- 重试找到更早历史时，不自动覆盖已经存在的日期标签，避免静默修改运营数据；
- 如未来需要更正已有标签，应作为独立、可审计的管理员操作实现。

日志只记录 Bot、Channel、conversationKey、数量、耗时和错误分类，不记录 Token 或完整客户消息正文。

## 历史消息导入规则

- 仅导入当前私聊 Chat ID 的消息；
- 保留收发方向、发送者、消息类型、文本、附件元数据、Whapi message ID 和原始发生时间；
- 复用现有会话消息展示和语义去重规则；
- provider message ID 是首要幂等键；
- 历史导入不得触发 Agent、自动回复、任务推进、标签 AI 判定或消息推送；
- 历史导入完成后，只有当前实时 webhook 消息可以触发现有业务流程。

## 日期标签规则

- 候选时间为成功解析的所有历史消息时间和当前消息时间；
- 选择最早候选时间；
- 调用现有 `dateTagIdFor` 与 Agent 日期标签配置中的 `cutoffTime`；
- 日期标签规则必须已启用；
- 对本地首次发现的新客户，即使规则启用时间晚于历史消息时间，也允许基于本次显式历史同步创建标签；
- 如果客户已经有日期标签，保持原值。

这一点与“启用日期标签时不批量回填所有历史客户”并不冲突：这里只处理首次进入本系统且正在产生实时消息的单个客户。

## 管理与可观察性

本阶段不增加后台批量按钮。同步在首次发现客户时自动运行。日志和数据库状态需能回答：是否尝试、拉取多少页、导入多少条、最早日期、最终状态和失败原因。

未来可以基于相同同步器增加管理员重试入口，但不纳入本次范围。

## 测试要求

- Whapi 客户端正确编码 Chat ID、分页和 Bearer Token；
- 本地未知客户会触发一次历史同步，已有客户不会触发；
- 多条并发 webhook 只执行一次同步；
- 历史分页、排序和最大数量边界正确；
- 历史消息与当前 webhook 按 message ID 去重；
- 历史导入不会调用 Agent 或发送 Channel 消息；
- 日期标签使用最早有效时间和现有截止时间规则；
- 已有日期标签不覆盖；
- Whapi 无历史或失败时，当前消息仍正常处理并使用当前日期；
- Token、响应正文和客户消息不会进入错误日志；
- 服务重启后能够恢复过期租约并安全重试。

## 非目标

- 不依赖联系人欢迎语判断新增客户；
- 不把 `contacts.post` 当作准确的新增好友事件；
- 不在服务启动时同步整个 Channel；
- 不批量覆盖现有客户的日期标签；
- 不承诺获得 WhatsApp 永久完整历史；
- 不让导入的历史消息重新触发自动化业务动作。
