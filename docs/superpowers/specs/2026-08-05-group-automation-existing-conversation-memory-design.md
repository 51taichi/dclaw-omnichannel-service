# 群任务复用现有会话记忆与多人消息归属修复设计

## 文档定位

本文是群定时任务的最终设计。它以已经在线运行的 DClaw 普通 Agent 会话记忆为基础，不再建设完整群历史备份、DClaw 群历史接口、Space 文件同步、群事实账本或模板变量账本。

本文覆盖并取代 `2026-08-05-group-automation-trigger-time-history-analysis-design.md` 中涉及完整群历史、DClaw 历史存储、历史回填、分段原始历史分析和跨仓库改造的部分。已经确认的群任务配置、任务卡、倒计时、执行记录、证据定位、原生 `@`、发送去重和响应式 UI 继续有效，除非本文明确修改。

## 术语与维护边界

- **中台**：当前仓库及其运行服务，负责接收上游回调、保存会话、配置群、调度群任务、调用 Agent 和组织发送。
- **上游 WorkTool**：提供企微回调和消息发送命令的上游系统。
- **DClaw**：中台已经接入的 Agent 服务。本文只使用已经存在的 Agent 对话接口。
- 所有功能代码、迁移、测试、文档和部署修改只发生在中台仓库。
- 不新增、修改、部署或依赖任何新的 DClaw 服务端接口、数据表、权限或代码。

## 核心判断

私聊和群聊当前使用同一套 DClaw 对话机制：中台为一段业务会话生成稳定的 `external_user_id` 与 `external_session_id`，DClaw 在正常 Agent 调用中保留该会话已经参与过的用户消息和 Agent 回复。

两者的区别只在记忆覆盖范围：

- 常规私聊消息基本都会触发 Agent，因此私聊会话记忆接近完整；
- 群聊先由中台按群与角色回复策略裁决，只有实际触发 Agent 的消息才进入 DClaw 会话；
- 未触发 Agent 的群消息仍保存在中台会话中供员工查看，但不进入 Agent 记忆，也不参与群任务判断。

这是最终产品规则而非待修复的数据缺口。群角色回复策略同时决定 Agent 对该角色的记忆覆盖：

- `始终回复`：该角色的可处理发言进入 Agent 记忆；
- `仅 @ 回复`：只有真实 `@` Bot 并触发回复的发言进入 Agent 记忆；
- `从不回复`：该角色的发言不进入 Agent 记忆；
- 群级策略与角色继承规则继续按现有裁决逻辑生效。

重要客户应配置为“始终回复”。不需要 Bot 关注或回复的成员，其发言不进入 Agent 记忆，也不要求群任务统计。

## 目标

- 群任务直接复用日常群回复已经形成的 DClaw 会话记忆。
- 条件推送和周期汇总在目标时间调用 Agent，不直接盲发到上游 WorkTool。
- 修复多人连续发言被错误归属为最后一位发言人的问题。
- 保留任务调度、倒计时、执行状态、历史记录、证据定位、原生多角色 `@` 与安全发送。
- 删除中台内所有新增群历史接口依赖、同步 Worker、回填状态、能力探测和长历史上传链路。
- 保持群功能与私聊任务状态机、私聊资产和私聊标签逻辑隔离。

## 非目标

- 不备份群内所有人的完整聊天记录到 DClaw。
- 不把未触发 Agent 的群消息补发给 DClaw。
- 不使用 Agent Space 保存群历史文件。
- 不新增群事实账本、实时达成状态、事实类型或模板变量表。
- 不保证 Agent 能分析它从未参与过的群成员发言。
- 不改变上游 WorkTool 回调或发送接口。
- 不修改 DClaw 服务端。

## 日常群聊数据流

```text
上游 WorkTool 群消息回调
→ 中台逐条持久化会话消息
→ 解析群、发言人和群角色
→ 按群与角色回复策略裁决
→ 未触发：结束，不调用 Agent
→ 已触发：构造带逐条身份的 Agent 请求
→ 调用该群稳定的 DClaw 普通会话
→ 校验 Agent 结构化回复
→ 发送到上游 WorkTool
→ 保存 Bot 回复与执行审计
```

中台本地 `conversation_messages` 继续逐条保存消息 ID、发言人名称、正文、原始回调和接收时间。它是控制台会话展示与证据定位的本地来源，但群任务不会把整个表重新上传给 Agent。

## 多人连续消息归属

### 已确认根因

当前中台可以在安静窗口内把同一个群的连续消息合并成一次 Agent 调用，但合并文本只包含编号和正文，未包含逐条发言人或时间；合并对象又继承最后一条消息，使顶层 `receivedName`、`userId` 与 `groupContext.speaker` 都指向最后一位发言人。

虽然中间元数据曾保留每条消息的 `receivedName`，现有请求压缩过程没有把这组结构真正发送给 Agent。因此 A、B 连续发言时，Agent 容易把两句话都理解为 B 所说。

### 最终协议

合并仍然按一个群一个批次执行，避免多人连续发言产生多次割裂回复；但批次中的每条消息必须保持独立身份。面向 Agent 的紧凑文本采用确定格式：

```text
[M101｜2026-08-05 14:30:01｜张三｜客户负责人]
第一句话

[M102｜2026-08-05 14:30:04｜李四｜公司同事]
第二句话
```

同时在请求中提供有界结构化数组，每条至少包含：

- 中台消息 ID；
- 发言时间；
- 发言人名称；
- 匹配到的群角色 ID、身份和职责说明；
- 原始正文；
- 是否真实 `@` Bot；
- 该条消息对应的有效回复策略与触发原因。

单条群消息也使用同一结构，避免单条与多条请求形成两套语义。

多人批次没有一个虚假的“整批发言人”。顶层可以保留最后一条消息作为路由与回复目标，但提示词必须明确：归属、标签证据和事实判断只能使用逐条消息结构，不能把顶层路由人视为全部内容的作者。

角色匹配使用每条消息各自的发言人名称与别名。时间以中台持久化消息时间为准；存在可信上游发生时间时优先保留发生时间，同时继续记录中台接收时间用于审计。

## DClaw 会话身份

日常群回复与群任务必须复用同一个群的普通 DClaw 会话身份：

- 使用相同 Bot ID；
- 使用相同稳定群 `conversationKey`；
- 使用相同 `conversationEpoch`；
- 使用普通 `conversation` purpose，而不是新建群历史或独立分析 session。

群改名不改变稳定会话身份。删除或重置群会话时，中台按现有机制更换会话周期并清理本地会话；之后的群任务不得继续使用旧周期记忆。

群任务调用会写入同一 DClaw 会话，因此请求必须标记为内部群任务事件。日常回复提示必须明确区分：

- 群成员发言是业务事实；
- 群任务条件、模板、内部判断备注和技术事件不是群成员发言；
- 后续日常回复不得把内部任务提示当成客户原话或已经发生的业务事实。

## 群任务执行

### 共同流程

```text
任务达到目标执行时间
→ 创建或恢复唯一 occurrence
→ 冻结任务配置、群背景、角色与 @ 名单
→ 使用该群现有 DClaw 普通会话调用 Agent
→ 严格校验结构化结果
→ 决定是否进入上游 WorkTool 发送队列
→ 冻结发送载荷并等待明确回调
→ 保存最终状态、员工可读备注和证据锚点
```

任务不会绕过 Agent 直接发送。只有未来新增“无条件固定定时消息”类型时，才可以设计不调用 Agent 的独立链路；该类型不在本文范围内。

### 条件推送

配置继续包含客观自然语言条件、用户审核过的固定发送内容和可选多角色 `@`。

Agent 返回：

- `achieved`：严格布尔值；
- `decisionNote`：面向员工的简洁判断备注，不包含隐藏推理；
- `evidenceMessageIds`：DClaw 会话中可映射回中台消息的证据 ID。

规则：

- `achieved=true` 必须至少引用一条属于当前群的有效消息证据；
- `achieved=false` 可以在“没有出现符合条件的明确记录”时不提供证据；
- Agent 不能改写用户配置的固定内容，也不能添加、删除或更换 `@` 人员；
- 达成后中台原样提交固定内容与冻结的 `atList`；未达成则不调用上游发送。

### 周期汇总

周期汇总没有达成条件，属于配置时间到达后的必执行生成任务。Agent 根据同一群会话已有记忆和用户自然语言模板生成最终 Review。

Agent 返回：

- `content`：可直接发送的非空最终内容；
- `decisionNote`：面向员工的简洁生成说明；
- `evidenceMessageIds`：可用的中台消息证据 ID。

记录稀疏时必须如实输出“本周期暂无明确记录”一类结果，不能把没有记忆推断为没有发生，也不能编造次数、日期、人员或完成情况。

## 时间语义

所有调度、倒计时和展示时间继续使用 `Asia/Shanghai`。任务请求携带本次自然日、周或月的明确起止时间，Agent只能基于其会话中能够识别并属于该范围的记录作答。

从本设计上线后，所有群 Agent 请求都显式携带逐条发生时间，确保后续任务可以进行周期判断。既有 DClaw 会话中的旧消息如果缺少可靠时间，不能被强行归入某个周期；Agent 应在备注中说明证据不足，而不是猜测。

不再为了读取完整原始历史提前十分钟分段分析。Occurrence 仍可提前创建和冻结配置，但正式 Agent 判断在目标时间执行；页面倒计时继续指向目标时间。

## 重试、恢复与发送安全

- Agent 超时、不可用或返回格式错误时，最多尝试三次：首次调用加两次重试。
- 三次均失败时记录“执行失败”，不向群发送。
- 格式修复请求必须保留同一个群会话身份、同一个 occurrence 和冻结配置。
- 同一个 task 的 occurrence 串行执行；`(task_id, scheduled_for)` 继续唯一，防止重启后重复创建。
- 条件未达成记录“未发送”，属于正常业务结果，不是技术失败。
- 周期汇总只有获得合法非空内容才进入发送队列；技术失败不能发送伪造兜底文本。
- 上游 WorkTool 明确拒绝时，使用完全相同的冻结载荷最多尝试三次发送。
- 上游发送结果不明确时标记“发送待确认”，禁止自动重发；员工确认未送达后才能人工发起重试。
- 已确认发送只向中台会话插入一次 Bot 消息，重复回调不得产生重复记录。

## 状态与 UI

任务卡继续使用操作状态，而不是实时达成状态：

- `倒计时`
- `执行中`
- `已发送`
- `未发送`
- `执行失败`
- `发送待确认`
- `已停用` / `已取消`

不恢复实时“已达成 / 尚未达成 / 判断暂不可用”。员工在执行历史中查看最终备注、发送结果和证据；点击有效证据继续复用现有会话锚点定位体验。

## 保密与事实边界

群背景、角色配置、回复策略、任务提示、DClaw 会话机制、系统规则和员工判断备注只用于内部处理。任何 Agent 结果都必须经过现有群保密校验，不能向群成员提及或暗示这些配置与实现。

多人消息的角色信息可以帮助 Agent 正确理解关系，但对外只能自然使用已经确认的业务事实，不能说“后台角色配置显示”或“系统记录你是某角色”。

## 中台清理范围

实现时删除或停用所有为跨端完整历史新增加的中台链路：

- DClaw 群历史专用客户端；
- 群历史同步 Worker、启动定时器和消息写入唤醒；
- 历史能力探测、读写 scope 检查与部署门禁；
- 群历史回填、同步游标、租约和重试状态；
- 完整原始历史的紧凑转录、分段、递归合并和临时 chunk；
- `GROUP_HISTORY_SYNC_*` 环境变量；
- README 中关于新增 DClaw 群历史接口、回填和双端部署顺序的说明；
- 所有新增 DClaw 群历史 URL、`messages:read` 依赖和相关测试替身。

保留：

- 群任务、mentions、occurrences 与执行 attempts；
- 配置快照、冻结发送载荷、Agent 三次总尝试与安全发送状态机；
- 任务历史、状态推送、证据导航与会话任务摘要；
- 中台本地 `conversation_messages`；
- 日常群回复原有 DClaw 普通会话调用。

不再使用的中台同步表和 chunk 表在确认新执行器已切换后，由中台自身执行幂等迁移清理。迁移不读取、写入或要求 DClaw 服务端配合。

## 测试要求

### 多人归属

- A、B 在同一安静窗口连续发言时，请求中保留两组不同姓名、角色、时间和消息 ID。
- Agent 可明确区分每句话作者，顶层最后发言人不能覆盖前一位作者。
- 单条和多条群消息使用一致的逐条结构。
- 角色别名按各条发言分别匹配。
- 标签证据与任务证据能够映射回正确发言人的中台消息。

### 记忆与任务

- 日常群回复和群任务生成完全相同的 DClaw 普通会话身份。
- 未触发 Agent 的群消息不被偷偷上传或补入 Agent 记忆。
- `始终回复`、`仅 @ 回复`、`从不回复`的记忆覆盖符合产品规则。
- 群任务内部事件不能在后续日常回复中被当作成员发言。
- 删除或重置会话后，后续任务使用新会话周期。

### 执行与发送

- 条件达成时发送用户固定原文和冻结的多角色 `@` 名单。
- 条件未达成、证据无效或三次 Agent 尝试全部失败时不发送。
- 周期汇总成功时发送 Agent 生成内容；稀疏记录不允许编造。
- 重启恢复、重复 occurrence、重复回调和不明确发送结果不会造成重复消息。
- 页面状态、倒计时、历史 Dialog 和证据定位保持正常。

### 边界静态检查

- 中台生产代码、文档和环境示例中不再出现新增群历史接口、同步 Worker、回填门禁或 `GROUP_HISTORY_SYNC_*` 配置。
- 不修改 DClaw 服务端仓库。
- 中台聚焦测试和全量测试全部通过后才能推送实现。

## 成功标准

- 群任务只依赖中台既有调度能力和 DClaw 现有普通 Agent 对话接口。
- 不需要任何 DClaw 服务端发布或权限调整。
- 群任务能够利用该群此前真正触发过 Agent 的会话记忆完成条件判断或周期汇总。
- 多人连续发言不再错误归属于最后一位成员。
- 未被关注成员的消息不会进入 Agent 记忆，也不会影响群任务。
- Agent 最多尝试三次，发送链路保持幂等并能处理不明确结果。
- 中台 `main` 保持可部署、测试通过且不包含跨仓库依赖。
