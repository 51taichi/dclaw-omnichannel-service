# 客户标签系统设计

## 目标

为每个 Agent 提供一套可配置、可导入导出的客户标签体系。标签用于在会话列表和会话详情中识别客户状态，并在标签变化时触发后续跟进话术。

本设计采用“Agent 判断，服务端裁决”的模式：DClaw Agent 根据客户消息和标签规则给出打标建议，控制台服务端负责校验、落库、取消旧任务和创建新任务。

## 边界

| 数据 | 归属 | 主键 |
| --- | --- | --- |
| 标签配置、标签组、触发任务模板 | Agent | `agentId` |
| 客户标签状态 | Bot + Agent + 会话 | `botId + agentId + conversationKey` |
| 标签变更记录 | Bot + Agent + 会话 | `botId + agentId + conversationKey` |
| 标签触发任务 | Bot + Agent + 会话 + 标签 | `botId + agentId + conversationKey + tagId` |
| 日期标签 | 服务端系统标签 | `botId + agentId + conversationKey + date` |

标签配置跟着 Agent 走。哪个 Bot 绑定该 Agent，控制台就显示该 Agent 的标签体系。客户业务数据仍然按照 `botId + agentId + conversationKey` 隔离，避免同一个 Agent 被多个 Bot 绑定时串客户。

## 标签类型

### 日期标签

日期标签是系统标签，不属于任何标签组。启用后，新增好友事件会为该客户自动打上当天日期，例如 `20260717`。

日期标签不交给 Agent 判断，也不允许 Agent 删除或修改。

### 互斥递进标签组

互斥标签组同一时间只能有一个标签。典型场景是意向等级：

```text
C类 -> B类 -> A类
```

标签排序决定递进方向。开启“单向递进”后，服务端只允许从低序位向高序位变化，不允许回退。例如客户已经是 `A类`，Agent 后续建议 `B类`，服务端拒绝该建议并保留 `A类`。

互斥组发生合法变化时：

1. 旧标签被替换。
2. 旧标签未发送的触发任务全部取消。
3. 新标签写入状态并启动新标签触发任务。

### 非互斥标签组

非互斥标签组中的多个标签可以同时存在。典型场景是客户特征、产品偏好、地区、来源渠道。

新增一个非互斥标签不会取消已有标签，也不会取消已有标签触发任务。只有该标签自身被移除或会话被清空时，才取消该标签的未发送任务。

第一版自动打标以“新增、递进、替换”为主，不做复杂的自动回退。后续如果需要“自动移除某个非互斥标签”，可以沿用同一套服务端裁决规则扩展。

## 标签配置模型

一个 Agent 可以配置多个标签组：

```json
{
  "agentId": "gujing_customer_service",
  "dateTag": {
    "enabled": true
  },
  "groups": [
    {
      "id": "intent_level",
      "name": "意向等级",
      "enabled": true,
      "exclusive": true,
      "oneWay": true,
      "tags": [
        {
          "id": "level_c",
          "name": "C类",
          "condition": "客户只是简单打招呼或泛泛了解，没有明确需求",
          "activation": {
            "enabled": false,
            "polishByAgent": true,
            "messages": []
          }
        },
        {
          "id": "level_b",
          "name": "B类",
          "condition": "客户开始询问产品、课程、资料或服务细节",
          "activation": {
            "enabled": true,
            "polishByAgent": true,
            "messages": [
              {
                "content": "刚才给您整理的内容看到了吗？有不清楚的我给您简单说说。",
                "intervalMinutes": 30,
                "maxTimes": 1
              }
            ]
          }
        }
      ]
    }
  ]
}
```

配置中的 `condition` 是给 Agent 判断的中文规则，不由服务端做关键词匹配。服务端只校验 Agent 返回的标签是否存在、是否启用、是否符合组规则。

## Agent 协议

服务端调用 DClaw Agent 时，除 WorkTool 标准消息、状态机和客户资产外，还会传入当前 Agent 的启用标签规则：

```json
{
  "tagRules": {
    "dateTagEnabled": true,
    "groups": [
      {
        "id": "intent_level",
        "name": "意向等级",
        "exclusive": true,
        "oneWay": true,
        "tags": [
          {
            "id": "level_b",
            "name": "B类",
            "condition": "客户开始询问产品、课程、资料或服务细节"
          }
        ]
      }
    ],
    "currentTags": [
      {
        "groupId": "intent_level",
        "tagId": "level_c",
        "name": "C类"
      }
    ]
  }
}
```

Agent 返回统一 JSON 回复对象时，可以附带 `tagDecision`：

```json
{
  "reply": "可以的，我给您简单介绍一下。",
  "attachments": [],
  "sources": [],
  "tagDecision": {
    "add": [
      {
        "groupId": "intent_level",
        "tagId": "level_b",
        "reason": "客户开始询问课程细节"
      }
    ],
    "remove": []
  }
}
```

`tagDecision` 是建议，不是事实。服务端可以接受、拒绝或部分接受建议，并记录原因。格式异常不会影响正常回复，但会记录结构化日志，方便排查 Agent 协议问题。

第一版中，`add` 用于新增、递进和互斥组替换；`remove` 只允许移除非互斥标签。互斥递进组不接受 Agent 的单独移除建议，避免把客户从已确认阶段清回空状态或低阶段。

## 服务端裁决

服务端按以下顺序处理标签建议：

1. 过滤未启用的标签组和标签。
2. 拒绝不存在的 `groupId` 或 `tagId`。
3. 拒绝 Agent 修改日期标签。
4. 对互斥组只保留一个目标标签。
5. 对开启单向递进的互斥组，拒绝回退变化。
6. 对非互斥组，新增标签不影响已有标签。
7. 对 `remove` 建议，只允许移除非互斥标签；互斥组移除建议会被拒绝。
8. 只有状态实际发生变化时，才写变更记录并处理触发任务。

每次裁决会写入标签事件：

```json
{
  "type": "tag_changed",
  "groupId": "intent_level",
  "oldTagIds": ["level_c"],
  "newTagIds": ["level_b"],
  "accepted": true,
  "reason": "客户开始询问课程细节",
  "source": "agent_decision"
}
```

被拒绝的建议也会写入日志，但不改变客户标签状态。

## 标签触发任务

每个标签可以配置触发话术，结构沿用现有“顺序激活话术”规则：

- 话术内容。
- 间隔分钟。
- 发送次数。
- 是否由 Agent 美化。

标签触发任务规则：

1. 标签首次打上时，启动该标签的话术任务。
2. 互斥组从旧标签变为新标签时，取消旧标签未发送任务，启动新标签任务。
3. 非互斥组新增标签时，只启动新标签任务，不影响已有标签任务。
4. 会话清空、人工接手、重新绑定 Agent、标签被移除时，取消相关未发送任务。
5. 客户普通回复不会直接取消标签任务，除非本次回复导致标签状态变化。
6. Worker 发送前必须重新校验该标签仍在当前会话标签状态中，避免旧任务误发。

标签任务和状态机节点激活任务是两套任务来源，但共用发送能力、Agent 美化能力和防误发校验。后续日志中需要区分来源为 `flow_activation` 或 `tag_activation`。

## 控制台

### 新增标签 Tab

标签 Tab 负责维护当前选中 Bot 所绑定 Agent 的标签配置：

- 日期标签开关。
- 标签组列表。
- 标签组启用开关。
- 互斥/非互斥设置。
- 单向递进开关。
- 标签排序。
- 标签名称和达标条件。
- 每个标签的触发话术配置。
- 导入和导出 JSON。

导入时按 `agentId` 写入当前 Agent 的标签配置，不覆盖其他 Agent。导出只导出标签配置，不导出客户标签状态。

### 会话 Tab

会话 Tab 增加：

- 会话卡片展示当前客户标签。
- 顶部增加标签筛选条件。
- 会话详情顶部展示完整标签状态。
- 标签 hover 展示命中原因、来源和时间。

标签展示必须节约空间，不挤压现有客户资产、任务状态和人工接手信息。

## 数据迁移

第一版新增表，不迁移旧业务数据：

- `agent_tag_schemas`：Agent 标签配置。
- `conversation_tags`：当前客户标签状态。
- `conversation_tag_events`：标签变更历史。
- `tag_activation_tasks`：标签触发任务队列。

没有标签配置的 Agent 不受影响。它仍然可以正常回复、记录会话、运行状态机和主动推送。

## 错误处理

- Agent 未返回 `tagDecision`：只发送正常回复，不打标。
- Agent 返回非法标签：拒绝该标签建议并记录日志。
- 标签任务创建失败：不影响客户回复，但记录 `tag.activation.schedule_failed`。
- 标签任务发送失败：按现有任务失败策略记录，避免无限重试。
- 标签配置导入失败：不写入半成品配置，返回可读错误。

## 测试

自动化测试覆盖：

1. 日期标签在新增好友事件中自动写入。
2. 无标签配置的 Agent 仍能正常回复和记录会话。
3. Agent 返回合法标签建议后，服务端写入客户标签状态。
4. 互斥组只能保留一个标签。
5. 单向递进组允许 `C -> B -> A`，拒绝 `A -> B`。
6. 非互斥组新增标签不会取消旧标签和旧任务。
7. 互斥组替换标签会取消旧标签未发送任务。
8. 标签任务发送前发现标签已失效时不会发送。
9. 会话筛选可以按标签过滤客户。
10. 标签配置导入导出不影响其他 Agent。

## 非目标

- 第一版不做复杂标签报表。
- 第一版不做客户批量改标签。
- 第一版不把标签规则写成关键词匹配引擎。
- 第一版不让 Agent 修改日期标签。
- 第一版不改变现有状态机归属规则。
