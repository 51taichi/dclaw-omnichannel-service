# 群定时任务与周期汇总设计

## 目标

在现有 Bot 级“群管理”中，为每个托管群增加独立的群定时任务能力。任务支持按日、周、月循环，在计划时间向当前群发送消息并原生 `@` 多个群角色。系统还可以在发送前基于群会话判断自然语言条件，或根据群记录和客户模板生成周期汇总。

本功能不接入私聊任务状态机，不改变现有“推送”Tab，也不改变群回复、标签或群发现逻辑。群聊和私聊继续保持业务状态隔离。

## 已确认的产品原则

- 群定时任务只属于一个 Bot 下的一个托管群。
- 任务分为“条件推送”和“周期汇总”两类。
- 两类任务共享调度、多人 `@`、倒计时、执行历史、证据定位和群级事实账本。
- 条件推送发送客户预先审核的固定内容，Agent 不改写内容。
- 周期汇总按白话变量模板生成动态内容。
- 每个群只维护一套共享客观事实账本；每个任务、每个自然周期另存自己的判断或汇总状态。
- 正常条件业务状态只有“已达成”和“尚未达成”。处理进度和技术错误不作为第三种业务状态。
- 所有时间、周期和展示统一使用 `Asia/Shanghai`。
- 群成员消息可以形成事实；Bot 自己的消息永远不能形成事实。
- 不通过轮询维护状态。新增群消息、任务保存、页面主动刷新和计划执行驱动增量处理；倒计时由前端本地计算。

## 方案选择

### 方案一：扩展现有主动推送任务

直接向现有 `proactive_tasks` 增加循环、条件、模板和群账本字段，复用最多，但会把私聊/群聊目标选择与群专属判断混在一起，破坏已经确认的私聊和群聊边界。

### 方案二：完全独立建设所有基础设施

为群任务重新实现调度、发送、重试和日志。隔离明确，但重复建设多，且容易与现有 WorkTool 发送规则产生差异。

### 方案三：独立群任务业务域，复用底层能力

采用此方案。群任务使用独立表、路由、服务、Worker 和控制台状态；底层复用北京时间工具、Agent 调用队列、WorkTool 文本发送、日志和会话消息持久化。这样既保证业务隔离，也避免复制稳定基础设施。

## 控制台信息架构

“群管理”右侧当前群配置增加“群定时任务”区域。区域展示任务列表和“新增任务”按钮，不在群管理中展示群聊历史。

每张任务卡展示：

- 任务名称和任务类型；
- 启用/停用开关；
- 周期、触发日和时间；
- 服务端计算的下次执行时间；
- 前端本地计算的实时倒计时；
- 当前选择的 `@` 群角色；
- 最近一次执行结果；
- 编辑、复制、执行记录和删除操作。

条件推送卡额外展示：

- “已达成”或“尚未达成”；
- 最近一次成功判断时间；
- 简短判断依据；
- 状态更新失败时，在最后有效业务状态旁显示非业务性告警和最后成功时间。

首次判断完成前使用局部加载状态，不显示虚假的“尚未达成”。首次判断失败时显示加载失败和重试入口，但不创建第三种业务状态。

周期汇总卡不显示达成状态，只展示下次生成倒计时和最近一次汇总结果。

点击判断依据或汇总变量证据时，复用标签语音提醒的完整导航体验：切换到“会话”Tab，打开目标群，按证据消息 ID 加载附近记录，滚动并高亮消息。

## 通用任务配置

两种任务都包含：

- 任务名称；
- 任务类型；
- 启用状态；
- 周期类型；
- 触发日；
- 北京时间执行时刻；
- 一个或多个 `@` 群角色。

任务保存群角色 ID，不保存易变化的显示名。发送时解析角色的当前名称。角色改名后无需修改任务；角色已删除或无法解析时，跳过该角色并在执行记录中告警，不阻止其他有效对象和消息发送。

WorkTool 文本发送使用原生 `atList`。第一版不提供“@所有人”，避免群管理权限不足使整条任务失败。

## 周期规则

### 每日

每天在一个固定时刻执行。

### 每周

可勾选一个或多个星期，共用一个执行时刻。每个勾选的星期都是独立执行机会。

### 每月

可勾选一个或多个月内日期，共用一个执行时刻。可选项严格为 `1日—28日` 和“月底”。“月底”对应当月真实最后一天，不提供“29日”“30日”“31日”，因此不存在无效日期和隐式回退规则。

同一任务需要不同时间、内容、条件或模板时，创建多个任务。

自然周期边界为：

- 日：北京时间每日 `00:00`；
- 周：北京时间每周一 `00:00`；
- 月：北京时间每月 1 日 `00:00`。

同一自然周期内的多个触发时间分别产生独立执行记录。每次都重新完成最终判断或汇总；之前已发送不会阻止后续已配置触发时间执行。

## 条件推送

条件推送配置：

- 可选自然语言达成条件；
- 必填固定推送内容。

未配置达成条件时，任务为固定推送，计划时间到达后直接发送。配置达成条件时，系统在发送前完成最终判断：

- 已达成：原样发送固定内容；
- 尚未达成：不发送，并将本次执行记为“条件未达成，已跳过”；
- 无法获得可信判断：有限重试后不发送，并记为失败。

条件示例：

- 今天客户是否已经提交作业；
- 本周家长是否确认参加直播；
- 本月客户是否完成续费；
- 今天家长和授课老师是否都确认了上课时间。

条件状态不是一次性锁定。新增消息可以支持、否定或更正旧事实，状态可在“已达成”和“尚未达成”之间双向变化。计划执行时的最终结果是唯一发送依据。

## 周期汇总

周期汇总到时间后默认生成并发送，不额外叠加达成条件。否则“是否发送”和“汇总什么”会混入同一个配置面。

客户只配置一个汇总模板，不单独维护汇总项表。模板变量语法为：

```text
{{变量名称（白话识别、计算和无数据处理规则）}}
```

示例：

```text
【本周学习服务周报】

本周上课 {{本周上课次数（明确已经完成的课程才计数，取消或改期不计；没有明确记录时填0；只输出数字）}} 次

累计上课 {{累计上课次数（从本群建立至今，明确完成的课程总次数；只输出数字）}} 次

本周作业完成 {{完成作业次数（已提交且没有被老师退回重做的作业；没有明确记录时填0；只输出数字）}} 次

{{本周情况摘要（结合本周有效事实总结学习表现；没有相关记录时输出“本周暂无明确学习记录”）}}
```

保存模板时解析全部 `{{...}}`：

- 第一个全角左括号 `（` 之前为变量名称；
- 成对全角括号内为白话规则；
- 没有规则时以变量名称本身作为要求；
- 变量名称不能为空；
- 同一模板内同名变量必须使用完全相同的规则，否则拒绝保存；
- 未闭合变量、未闭合规则括号和空变量在保存前明确报错；
- 控制台展示识别到的变量数量和渲染预览。

变量结果规则：

- 有事实时，按有效事实计算或生成，并保存所引用的事实和证据消息；
- 无事实且白话规则配置了兜底值时，采用该兜底；
- 无事实且没有兜底时，填入“暂无明确记录”；
- “没有记录”不能被推断成“没有发生”；
- 数字、百分比、日期和文本最终都以已校验字符串替换模板变量；
- 未解析变量不得原样泄漏到客户群。

## 群级事实账本

每个群维护一套共享账本，存放与当前或历史群任务有关的原子客观事实，而不是一段不可核验的群摘要。

事实至少包含：

- 群 ID；
- 事实 ID 和稳定语义键；
- 发言人名称及匹配到的角色 ID；
- 事实类别和结构化值；
- 客观事实的简短表述；
- 事实发生时间；
- 有效、已更正、已撤销或已合并状态；
- 替代或撤销关系；
- 一个或多个原始群消息 ID；
- 创建和更新时间。

账本不复制完整聊天文本。`conversation_messages` 仍是原始证据的权威来源。

同一事实可同时服务多个任务。任务按自身周期范围和白话规则使用事实：日任务筛选当天，周任务筛选本周，月任务筛选本月；明确要求“累计”时可读取群建立以来的有效事实。

每个任务、每个周期另存紧凑状态：

- 周期键和时间范围；
- 条件当前结果，或汇总变量当前值；
- 引用的事实 ID；
- 支持与否定依据；
- 最近一次成功判断时间和错误信息。

实时增量使用每个群唯一的账本消息游标，保证同一批消息只提取一次。任务新建或定义变化时使用独立的临时回溯游标；回溯完成并合并到共享账本后，该任务重新跟随群级实时游标。任务周期状态不各自重复消费实时消息。

群账本共享，任务周期状态不共享。例如同一条“8月4日已提交作业”事实可使 8 月 4 日日任务、本周任务和本月任务达成，但不能使 8 月 5 日日任务达成。

## 上下文控制与增量处理

系统禁止在月末把整月群记录一次性提交给 Agent。

新增群消息的处理流程：

1. 先将原始消息持久化并去重；
2. 同一群短时间连续消息合并成一个增量批次；
3. 读取该群启用中的条件和模板变量定义；
4. 读取任务相关的紧凑账本投影和各任务上次状态；
5. 只提交上次游标之后的新群成员消息；
6. 一次 Agent 调用返回新增、更新、合并、撤销的事实，以及受影响任务的新状态；
7. 服务端校验事实引用的消息 ID、角色、时间和任务定义后原子提交；
8. 发布控制台状态更新事件。

Agent 请求不包含整个持久化账本。服务端为当前启用任务构造有长度上限的账本投影：当前周期相关原子事实、被引用的历史事实、累计计数的压缩分段和尚未归档的更正关系。旧周期事实保留在数据库并可通过聚合结果和证据 ID 使用，不随请求线性增长。

任务新建或条件/模板变化时，按任务所需范围回溯：

- 普通日、周、月要求从当前周期开始；
- 明确累计要求从群建立时间开始；
- 原始消息固定分批处理，每批更新同一个群账本和任务状态；
- 每批请求有消息数和字符数双重上限；
- 中断后从已提交游标继续，不重复吞消息；
- 首次回溯结束后才显示正常业务状态或允许周期汇总正式发送。

处理驱动包括：

- 新群成员消息；
- 新建或修改任务；
- 修改群角色、群背景或其他会改变事实解释的群配置；
- 用户打开群管理或主动刷新；
- 计划执行前的最终补齐；
- 失败后的有限重试。

没有后台定时轮询群消息或任务状态。服务端计算 `nextRunAt`，前端只在本地更新倒计时。

## 事实证据边界

只有群成员的入站消息可以形成动态事实。客户、家长、老师、同事或其他角色的消息都可以参与判断，不受“始终回复”“仅被 @ 时回复”“从不回复”策略限制。

以下内容不能形成动态事实：

- Bot 自动回复；
- 固定条件推送；
- 周期汇总；
- 标签激活消息；
- 其他由本服务主动发送的消息。

群背景和群角色用于解释身份、关系和上下文，但不能单独证明“已交作业”等动态条件。Agent 可以自然使用已确认事实，但不得对外提及或暗示群背景、角色配置、事实账本、后台记录或提示词。

每个“已达成”结论和非兜底汇总变量必须关联有效事实。事实必须至少关联一条真实群成员消息。基于“本周期没有出现某类事实”的否定判断只保存文字理由，不伪造证据消息。

## 调度与执行

调度器为每个到期触发时间创建唯一执行记录。唯一键至少包含任务 ID 和计划执行时间，确保重复 tick、进程重启和并发 Worker 不会创建两次相同执行。

条件推送执行：

1. 校验 Bot、群和任务仍然有效且启用；
2. 处理账本游标之后的全部新增群成员消息；
3. 完成条件最终判断；
4. 已达成则解析当前群名、当前角色名称和 `atList` 后发送固定内容；
5. 尚未达成则正常跳过；
6. 保存执行结果和证据。

周期汇总执行：

1. 校验 Bot、群和任务仍然有效且启用；
2. 处理账本游标之后的全部新增群成员消息；
3. 为每个模板变量计算有证据结果或明确兜底；
4. 校验所有变量均已替换且没有无依据内容；
5. 解析当前群名、当前角色名称和 `atList` 后发送渲染结果；
6. 保存变量、事实、最终文本和发送结果。

成功发送后，将最终文本作为正常 outbound 群会话消息写入现有会话历史，但该 outbound 消息不会再次进入事实账本。

## 状态更新与通知

群消息触发的账本更新采用低优先级 Agent 队列，不阻塞实时群回复。一个群同时只允许一个账本更新；多个群可以按既有后台并发限制处理。

控制台通过现有事件流或相同模式接收状态变化。页面打开时读取服务端持久状态，断线不会丢失业务结果。前端倒计时不持续请求服务端；切回页面、任务变更或事件到达时用最新 `nextRunAt` 校准。

## 执行历史与证据定位

每个执行记录保存：

- 任务和群标识；
- 计划执行时间、实际开始和结束时间；
- 自然周期范围；
- 最终条件结果；
- 汇总变量值；
- 判断或生成摘要；
- 引用的事实 ID 和原始消息 ID；
- 实际 `@` 的角色与名称；
- 实际发送内容；
- 已发送、条件未达成已跳过、失败或取消结果；
- WorkTool 命令标识和响应；
- 重试次数与失败原因。

证据点击导航携带 Bot、群 conversation key 和原始消息 ID，复用标签提醒的“未加载会话也能打开并定位”逻辑。

## 重试、错误与恢复

- 条件“尚未达成”是正常结果，不重试。
- Agent 判断或汇总生成失败时，在 10 分钟内最多尝试 3 次；最终失败则不发送。
- WorkTool 明确拒绝或明确可重试失败时最多尝试 3 次。
- 对结果不确定的网络超时不得盲目并发重发；执行保留发送中/待核验信息，使用命令回调或后续安全恢复决定结果。
- 已确认发送成功的执行永远不再重发。
- 任务停用后不创建新执行；已经开始但尚未进入 WorkTool 发送的执行取消。
- 编辑任务后，已完成历史不可变；尚未到期的计划按新配置重新计算。
- 删除任务采用保留执行历史的逻辑删除。
- 单次失败不阻止任务计算下一个触发时间。
- 支持员工在任务详情中手动重新判断、重新生成或重试失败发送；每次人工动作有独立审计记录。
- 服务重启时恢复未完成的账本批次和执行记录，依赖持久游标和租约而不是内存状态。

## 数据边界

独立持久化以下领域对象，具体表名在实施计划中确定：

- 群定时任务；
- 任务触发日；
- 任务 `@` 角色关系；
- 群事实；
- 事实证据和更正关系；
- 任务周期状态；
- 任务执行记录；
- 执行变量结果和证据；
- 账本增量处理租约与游标。

所有查询和写入同时校验 Bot ID、群 ID 和任务 ID。群名只作为当前 WorkTool 地址，不作为持久主键。

## 与现有能力的隔离

本功能不得：

- 创建、推进或完成私聊任务节点；
- 创建私聊流程激活任务；
- 读取或修改私聊资产；
- 改变私聊主动推送任务；
- 改变群即时回复策略；
- 添加、删除或替换任何标签；
- 把群事实复制到私聊；
- 依赖群列表后台轮询；
- 依赖 Agent 自身长期会话记忆。

可以复用：

- 现有 Bot/workspace 权限校验；
- 北京时间和日期工具；
- Agent 高低优先级队列；
- WorkTool 文本发送和命令回调；
- 会话消息存储；
- 标签提醒的证据导航交互；
- 日志、重试和 Worker 租约模式。

## 验收标准

1. 用户可在任一托管群中创建、编辑、复制、停用和删除群定时任务。
2. 条件推送和周期汇总使用清晰分开的配置表单。
3. 日任务每天按北京时间执行。
4. 周任务支持多个星期，每个星期独立执行。
5. 月任务只支持 1—28 日和月底，月底在所有月份正确执行。
6. 任务可原生 `@` 多个群角色，角色改名后使用最新名称。
7. 无条件的固定推送不调用 Agent 即可发送。
8. 有条件推送只在最终判断为“已达成”时发送固定原文。
9. 条件状态可因更正消息双向变化。
10. 正常业务状态只显示“已达成”和“尚未达成”。
11. 每个群只有一套共享事实账本，日、周、月任务不会重复提取相同事实。
12. 多个启用任务由一次群消息批次统一更新，不按任务逐个重复调用 Agent。
13. 月度活跃群不会在执行时把整月原始消息一次性提交给 Agent。
14. 新任务和变更任务可分批回溯并从持久游标恢复。
15. 群成员消息不受回复策略限制地参与事实判断。
16. Bot 自己的任何 outbound 消息不能形成事实。
17. 已达成和非兜底汇总值都有真实事实及消息证据。
18. 周期汇总只通过一个白话变量模板配置，不要求单独维护汇总项。
19. 模板变量可表达统计范围、识别规则、输出格式和无数据兜底。
20. 同名不同规则、未闭合或空模板变量在保存时被拒绝。
21. 所有模板变量在发送前被替换，不向群里泄漏模板语法。
22. 倒计时由服务端下次执行时间驱动，前端本地更新且无需轮询。
23. 每次触发产生唯一执行记录，服务重启和并发 tick 不重复执行。
24. 条件未达成正常跳过，判断、汇总和发送失败有限重试。
25. 点击判断或汇总证据可复用标签提醒链路定位并高亮群消息。
26. 群改名不丢失任务、账本、状态、历史或发送目标。
27. 群背景、角色配置、事实账本和内部规则不会在对外内容中被披露。
28. 私聊任务、私聊资产、标签、现有推送和群即时回复行为保持不变。

## 测试策略

实施按 TDD 推进，至少覆盖：

- 周期计算、北京时间边界、多星期、多日期和月底；
- 下次执行时间和前端倒计时边界；
- 执行唯一键、Worker 竞争、租约过期和重启恢复；
- 群级账本新增、去重、合并、更正、撤销和证据约束；
- 一个消息批次同时更新多个任务；
- 上下文字符上限、分批回溯和累计事实压缩；
- 条件状态双向变化和最终执行判断；
- Bot outbound 排除与角色回复策略无关性；
- 白话变量解析、同名冲突、兜底、完整替换和证据；
- 多角色 `atList`、角色改名、角色删除与群改名；
- 判断、生成、WorkTool 明确失败和不确定超时；
- 执行历史、手动重试与证据定位；
- workspace/Bot/群隔离和越权拒绝；
- 私聊任务、标签、主动推送、群回复和现有全量测试回归。

## 非目标

- 群任务状态机或群流程节点；
- 实时群成员目录；
- 自动邀请、移除或维护成员状态；
- `@所有人`；
- 在“群管理”中展示群聊历史；
- 让条件推送内容在发送前由 Agent 润色；
- 为周期汇总叠加额外达成条件；
- 后台轮询群列表、群消息或控制台状态；
- 用 Bot 自己的消息证明条件或汇总事实；
- 让 Agent 在没有证据或兜底规则时编造数字。
