# Single-Call Agent Tag Audit Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make every tag-enabled Agent response explicitly evaluate all enabled tags in the existing single call, persist the result for audit, and recover correctly when the live voice-alert stream loses authentication.

**Architecture:** Add a focused `tag-audit` module that normalizes and validates the new `tagEvaluation` contract. DClaw request builders place a compact mandatory audit block before reply instructions, the existing gateway rejects incomplete audits and uses its current repair call, and the server persists only final valid evaluations before applying the existing tag adjudicator. The console alert stream reports HTTP 401 as authentication expiry instead of retrying a dead token.

**Tech Stack:** Node.js 22 ESM, built-in `node:test`, `node:sqlite` `DatabaseSync`, Express 5, browser Fetch streams, existing DClaw OpenAPI client.

## Global Constraints

- Normal inbound processing must still make one Agent call.
- A second call is allowed only through the existing response-repair path after a contract failure.
- Do not modify the conversation identity, lifecycle, cleanup, or queue behavior introduced by `9d24511`.
- Do not require changes to any Agent workspace.
- Historical analysis remains customer-only and bounded to the configured 1000-6000 character limit.
- Existing server adjudication remains authoritative for exclusivity, one-way changes, and manual overrides.
- Only accepted `add` or `replace` outcomes create tag activations or voice alerts.
- Keep the work on the current `main` checkout; do not create an isolated worktree.

function persistAgentTagAudit({

    invocationId,
    evaluationCount: records.length,
